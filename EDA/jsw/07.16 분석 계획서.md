# EDA 담당 2 사전 분석 계획서

## 0. 현재 상태

- 담당 범위: `bureau.csv`, `bureau_balance.csv`
- 분석 주제: 외부 금융기관 신용거래와 월별 연체 이력
- 현재 단계: **원본 데이터를 열기 전 작성한 사전 계획**
- 이 문서는 실제 분석 결과가 아니라, 데이터를 확인할 때 무엇을 어떤 순서로 점검할지 정한 실행 계획이다.
- 아래 컬럼명과 상태값은 `EDA_4인_역할분담.md`에 정리된 Home Credit 구조를 기준으로 작성했다. 실제 구현 전 `data/HomeCredit_columns_description.csv`와 실제 CSV 헤더를 대조한다.

## 1. 분석 목적

현재 대출 신청 고객의 외부 신용이력을 고객 단위로 요약하고, 다음 질문에 답한다.

1. 외부 신용거래를 많이 보유하거나 활성 거래 비중이 높은 고객은 어떤 특성을 보이는가?
2. 총부채, 신용공여액 대비 부채 비율, 현재 연체금액은 `TARGET`과 어떤 관계가 있는가?
3. 과거의 일시적인 연체와 최근에도 지속되는 연체를 구분할 수 있는가?
4. 최근 3·6·12개월 동안 연체 빈도와 연체 심도가 악화되는 고객을 찾을 수 있는가?
5. 외부 신용이력이 없는 고객, 월별 이력이 없는 고객, 이력이 충분한 고객 사이에 차이가 있는가?

`TARGET=1`은 대출 승인 거절이 아니라 상환곤란을 뜻한다. 따라서 결과는 관측된 상관관계로만 해석하며, 승인 가능성이나 인과효과를 주장하지 않는다.

## 2. 가장 먼저 확인할 사항

### 2.1 테이블 관계

분석 단위가 서로 다르므로 다음 순서를 반드시 지킨다.

```text
bureau_balance: 월별 상태 여러 행
        ↓ SK_ID_BUREAU 단위 집계
bureau: 외부 신용계약 1행
        ↓ SK_ID_CURR 단위 집계
고객별 외부 신용 피처 1행
        ↓
application_train/test의 고객 ID와 결합
```

- `bureau.csv`: 한 고객(`SK_ID_CURR`)이 여러 외부 신용계약(`SK_ID_BUREAU`)을 가질 수 있다.
- `bureau_balance.csv`: 한 신용계약이 여러 월(`MONTHS_BALANCE`)의 상태를 가질 수 있다.
- 원시 `bureau_balance` 행을 Application 데이터에 직접 결합하지 않는다.
- 최종 산출물은 반드시 `SK_ID_CURR`당 1행이어야 한다.

### 2.2 키와 중복

가장 먼저 아래 항목을 표로 기록한다.

- `bureau.SK_ID_BUREAU`가 유일한지
- `bureau_balance`의 `SK_ID_BUREAU + MONTHS_BALANCE` 조합이 유일한지
- `bureau_balance`에는 있지만 `bureau`에는 없는 고아 `SK_ID_BUREAU`가 있는지
- `bureau.SK_ID_CURR`가 train/test 고객 ID에 얼마나 연결되는지
- 한 고객이 보유한 계약 수와 한 계약이 보유한 월별 관측 수의 분포
- 완전 중복 행과 키는 같지만 값이 다른 충돌 행의 수

중복은 바로 삭제하지 않고 원인을 구분한다. 완전 중복, 키 충돌, 정상적인 반복 거래를 각각 따로 집계한다.

### 2.3 자료형과 코드값

- ID 컬럼은 수치형 설명변수가 아니라 연결 키로만 사용한다.
- `STATUS`의 실제 값이 `0`~`5`, `C`, `X`로 구성되는지 확인한다.
- `C`는 종료, `X`는 상태 미상으로 다루며 정상 상태 `0`과 합치지 않는다.
- 금액, 일수, 월 변수의 자료형과 결측률을 확인한다.
- 범주형 컬럼은 고유값, 빈도, 희소 범주, 예상하지 못한 코드값을 확인한다.

## 3. 데이터 품질 및 이상치 탐지 계획

이상치는 무조건 제거할 값이 아니다. **입력 오류 후보**, **논리 불일치**, **실제 극단 고객**을 구분해 플래그로 보존한다.

### 3.1 결측치

각 변수에 대해 전체 결측률뿐 아니라 아래를 함께 확인한다.

- `CREDIT_ACTIVE`, `CREDIT_TYPE` 등 계약 상태별 결측률
- train 고객과 test 고객의 결측률 차이
- `TARGET=0`과 `TARGET=1`의 결측률 차이
- 특정 금액이 결측일 때 관련 금액도 함께 결측되는지
- `bureau` 이력은 있지만 `bureau_balance` 이력이 없는 계약의 비율

결측 자체가 정보를 가질 수 있으므로 주요 변수에는 `IS_MISSING_<COLUMN>` 후보를 검토한다. 이력이 없는 고객은 결측 고객과 구분해 `HAS_BUREAU=0`으로 표시한다.

### 3.2 수치형 극단값

금액·일수·계약 수 변수에 다음 방법을 함께 적용한다.

- 최소, 최대, 평균, 중앙값, 표준편차
- 1·5·25·50·75·95·99백분위
- IQR 기준 극단값 수
- 중앙값과 MAD를 이용한 강건 Z-score
- 양수 금액은 `log1p` 분포도 함께 확인

IQR 또는 백분위 기준을 벗어났다는 이유만으로 행을 삭제하지 않는다. 원본값을 유지하고 `OUTLIER_*` 플래그를 만든 뒤, 시각화에서만 로그축 또는 1~99백분위 표시 범위를 사용한다.

### 3.3 값 범위 점검

예상 컬럼이 실제로 존재할 경우 다음 후보를 확인한다.

- `DAYS_CREDIT`, `DAYS_CREDIT_UPDATE`가 신청 시점 기준 과거 일수 규칙을 따르는지
- `DAYS_CREDIT_ENDDATE`는 예정 종료일이므로 양수도 가능하다는 점을 구분하는지
- `MONTHS_BALANCE`가 신청 시점 기준 0 이하인지
- `CREDIT_DAY_OVERDUE`, `CNT_CREDIT_PROLONG`, 금액 변수가 음수인지
- `STATUS`가 정의된 코드 밖의 값을 갖는지
- 동일 계약 내 `MONTHS_BALANCE`가 중복되거나 중간 월이 비어 있는지

변수 정의를 확인하기 전에는 단순히 양수 또는 음수라는 이유만으로 오류로 확정하지 않는다.

### 3.4 계약 내 논리 일관성

아래 조건은 삭제 기준이 아니라 검토용 품질 플래그로 만든다.

- 총부채가 신용공여액보다 큰 계약
- 연체금액이 총부채보다 큰 계약
- 종료 상태인데 실제 종료일이 없는 계약
- 활성 상태인데 실제 종료일이 기록된 계약
- 현재 연체일은 0인데 연체금액이 양수인 계약
- 월별 최악 연체 상태와 `bureau`의 현재 연체 정보가 크게 다른 계약
- 월별 상태가 `C` 이후 다시 활성 연체 코드로 바뀌는 계약

이 차이는 오류일 수도 있지만 서로 다른 기준시점 때문에 생길 수도 있으므로, 빈도와 사례를 확인한 뒤 해석한다.

## 4. 파생변수 설계

파생변수는 월별 계약 수준, 고객 수준의 두 단계로 만든다. 처음부터 모든 후보를 한꺼번에 만들지 않고 우선순위 A부터 검증한다.

### 4.1 `bureau_balance` → 계약 단위 피처

#### 우선순위 A: 기본 상태와 최근 연체

| 피처 | 정의 |
|---|---|
| `BB_OBS_MONTH_COUNT` | 해당 계약의 관측 월 수 |
| `BB_MIN_MONTH`, `BB_MAX_MONTH` | 가장 오래된 월과 가장 최근 월 |
| `BB_HISTORY_SPAN_MONTHS` | 관측 기간 길이 |
| `BB_MISSING_MONTH_COUNT` | 관측 기간 중 빠진 월 수 |
| `BB_STATUS_0_RATIO` | 정상 상태 월 비율 |
| `BB_CLOSED_RATIO` | `C` 상태 월 비율 |
| `BB_UNKNOWN_RATIO` | `X` 상태 월 비율 |
| `BB_DELINQUENT_MONTH_COUNT` | `STATUS=1~5`인 월 수 |
| `BB_DELINQUENT_MONTH_RATIO` | 연체 월 수 / 상태가 확인된 유효 월 수 |
| `BB_MAX_STATUS` | 관측된 최악 연체 심도 |
| `BB_DELINQUENT_COUNT_3M` | 최근 3개월 연체 월 수 |
| `BB_DELINQUENT_COUNT_6M` | 최근 6개월 연체 월 수 |
| `BB_DELINQUENT_COUNT_12M` | 최근 12개월 연체 월 수 |

최근 기간창은 `MONTHS_BALANCE`의 실제 기준을 먼저 확인한 후 정의한다. 예를 들어 최신 월이 0이라면 최근 3개월은 `-2~0`으로 계산한다.

#### 우선순위 B: 지속성·최근성·회복

| 피처 | 정의 |
|---|---|
| `BB_MONTHS_SINCE_LAST_DELINQUENCY` | 마지막 연체 이후 경과 월 |
| `BB_LONGEST_DELINQUENT_STREAK` | 연속 연체의 최장 개월 수 |
| `BB_SEVERE_DELINQUENT_COUNT` | `STATUS=3~5` 월 수 |
| `BB_RECENT_MAX_STATUS_3M` | 최근 3개월 최악 상태 |
| `BB_RECENT_MAX_STATUS_12M` | 최근 12개월 최악 상태 |
| `BB_RECOVERY_FLAG` | 연체 뒤 정상 또는 종료 상태로 회복했는지 |
| `BB_WORSENING_FLAG` | 최근 상태의 연체 심도가 과거보다 악화됐는지 |
| `BB_STATUS_TRANSITION_COUNT` | 상태가 바뀐 횟수 |

`X`와 `C`는 숫자 연체 심도로 변환하지 않는다. 최악 상태와 추세 계산에서는 `0~5`만 사용하고, `X`와 `C`의 비율은 별도 피처로 보존한다.

### 4.2 `bureau` → 고객 단위 피처

#### 우선순위 A: 계약 수·활성 상태·금액

| 피처 | 정의 |
|---|---|
| `HAS_BUREAU` | 외부 신용이력 존재 여부 |
| `BUR_CREDIT_COUNT` | 외부 신용계약 수 |
| `BUR_ACTIVE_COUNT` | 활성 계약 수 |
| `BUR_CLOSED_COUNT` | 종료 계약 수 |
| `BUR_ACTIVE_RATIO` | 활성 계약 수 / 전체 계약 수 |
| `BUR_CREDIT_TYPE_NUNIQUE` | 외부 신용상품 종류 수 |
| `BUR_TOTAL_CREDIT` | `AMT_CREDIT_SUM`의 고객별 합 |
| `BUR_TOTAL_DEBT` | `AMT_CREDIT_SUM_DEBT`의 고객별 합 |
| `BUR_ACTIVE_DEBT` | 활성 계약의 부채 합 |
| `BUR_TOTAL_OVERDUE` | `AMT_CREDIT_SUM_OVERDUE`의 고객별 합 |
| `BUR_DEBT_CREDIT_RATIO` | 총부채 / 총 신용공여액 |
| `BUR_OVERDUE_DEBT_RATIO` | 총 연체금액 / 총부채 |
| `BUR_MAX_DAYS_OVERDUE` | `CREDIT_DAY_OVERDUE`의 최대값 |
| `BUR_RECENT_CREDIT_DAYS` | 가장 최근 외부 신용개설 이후 기간 |

비율의 분모가 0 이하이거나 결측이면 결과를 `NaN`으로 두고 `INVALID_DENOM_*` 플래그를 만든다. 계약별 비율의 평균보다 **고객별 합계의 비율**을 우선 사용한다.

#### 우선순위 B: 분포·기간·갱신 정보

| 피처 | 정의 |
|---|---|
| `BUR_MEAN_CREDIT`, `BUR_MAX_CREDIT` | 계약 금액의 평균·최대 |
| `BUR_MEAN_DEBT`, `BUR_MAX_DEBT` | 부채의 평균·최대 |
| `BUR_DEBT_CONTRACT_COUNT` | 부채가 남아 있는 계약 수 |
| `BUR_OVERDUE_CONTRACT_COUNT` | 현재 연체가 있는 계약 수 |
| `BUR_PROLONG_TOTAL` | 신용 연장 횟수 합 |
| `BUR_DAYS_SINCE_LAST_UPDATE` | 가장 최근 외부 신용정보 갱신 이후 기간 |
| `BUR_ACTUAL_CREDIT_DURATION` | 신용개설일부터 실제 종료일까지의 기간 |
| `BUR_PLANNED_END_GAP` | 예정 종료일과 실제 종료일의 차이 |
| `BUR_CREDIT_TYPE_<TYPE>_RATIO` | 주요 신용상품별 계약 비율 |

희소한 `CREDIT_TYPE`은 원본 범주를 보존하면서 시각화용으로만 `OTHER`로 묶는다.

### 4.3 월별 이력과 계약 정보를 결합한 고객 피처

| 피처 | 정의 |
|---|---|
| `HAS_BUREAU_BALANCE` | 월별 외부 신용상태 이력 존재 여부 |
| `BB_COVERED_CREDIT_RATIO` | 월별 이력이 있는 계약 수 / 전체 외부 계약 수 |
| `BB_DELINQUENT_CREDIT_RATIO` | 한 번이라도 연체된 계약 비율 |
| `BB_SEVERE_DELINQUENT_CREDIT_RATIO` | `STATUS=3~5`를 경험한 계약 비율 |
| `BB_CUSTOMER_MAX_STATUS` | 고객의 전체 계약 중 최악 연체 심도 |
| `BB_CUSTOMER_DELINQUENT_COUNT_3M` | 전체 계약의 최근 3개월 연체 월 수 합 |
| `BB_CUSTOMER_DELINQUENT_COUNT_6M` | 전체 계약의 최근 6개월 연체 월 수 합 |
| `BB_CUSTOMER_DELINQUENT_COUNT_12M` | 전체 계약의 최근 12개월 연체 월 수 합 |
| `BUR_ACTIVE_WITH_RECENT_DELINQ_COUNT` | 활성 계약이면서 최근 연체가 있는 계약 수 |
| `BUR_CURRENT_VS_HISTORY_RISK_FLAG` | 현재 연체 정보와 과거 최악 상태가 불일치하는지 |

고객별 연체 월 비율은 계약별 비율을 단순 평균하지 않고, 유효 관측 월 수를 분모로 한 가중 집계를 기본으로 한다.

## 5. 기초 EDA 실행 순서

### 1단계: 구조와 품질

1. 행·열 수, 키, 자료형, 메모리 사용량을 확인한다.
2. 키 중복과 고아 키를 확인한다.
3. 결측률, 범주 빈도, 수치형 백분위를 확인한다.
4. 상대 날짜와 상대 월의 방향을 공식 설명과 대조한다.
5. 논리 불일치와 극단값 플래그를 만든다.

### 2단계: 계약과 월별 이력

1. 고객당 계약 수 분포를 확인한다.
2. 계약 상태, 신용상품 종류, 통화 범주를 확인한다.
3. 계약당 월별 관측 길이와 누락 월을 확인한다.
4. 정상·연체·종료·미상 상태 비율을 확인한다.
5. 최근 3·6·12개월 연체 빈도와 최악 심도를 만든다.

### 3단계: 고객 단위 집계

1. `bureau_balance`를 `SK_ID_BUREAU` 단위로 집계한다.
2. 집계 결과를 `bureau`에 연결한다.
3. 계약 정보를 `SK_ID_CURR` 단위로 다시 집계한다.
4. 최종 고객 테이블에서 `SK_ID_CURR` 유일성을 검증한다.
5. 거래가 없는 고객과 결측 고객을 구분한다.

### 4단계: `TARGET` 및 train/test 비교

고객 단위 집계가 끝난 뒤에만 Application 데이터의 ID와 결합한다.

- train: `SK_ID_CURR`, `TARGET`만 연결
- test: `SK_ID_CURR`만 연결
- 외부 신용이력 보유율의 train/test 차이
- 주요 피처의 train/test 분포 차이
- `TARGET`별 중앙값, 분위수, 이력 보유율, 연체율 비교
- 구간별 상환곤란률과 95% Wilson 신뢰구간

표본 수가 작은 범주의 높은 상환곤란률을 중요한 패턴으로 과대해석하지 않는다.

## 6. 우선 시각화

최소한 아래 그래프를 우선 작성한다.

1. 고객당 외부 신용계약 수 분포와 `TARGET`별 비교
2. 활성 계약 비율 구간별 고객 수와 상환곤란률
3. 총부채와 총 신용공여액 산점도(로그축, `y=x` 기준선)
4. 부채/신용공여액 비율 구간별 상환곤란률
5. 최악 월별 연체 상태별 고객 수와 상환곤란률
6. 최근 3·6·12개월 연체 고객 비율 비교
7. 최근 연체와 과거 연체만 있는 고객의 상환곤란률 비교
8. 외부 신용이력 없음 / 계약만 있음 / 월별 이력 있음 그룹 비교
9. 주요 피처의 train/test 분포 비교

모든 그래프에는 제목, 축 단위, 표본 수 또는 분모, 결측 처리 기준을 표시한다.

## 7. 분석 시 주의할 점

- ID를 연속형 변수처럼 평균 내거나 상관분석에 사용하지 않는다.
- `STATUS`의 `C`, `X`를 임의의 숫자 순서로 변환하지 않는다.
- 계약 수가 많은 고객이 월별 행을 많이 가진다는 이유로 분석에서 과도한 가중치를 받지 않도록 고객 단위로 집계한다.
- 이력이 없는 고객을 금액 0인 고객과 동일하게 처리하지 않는다.
- 금액 극단값을 확인 없이 삭제하거나 winsorize하지 않는다.
- 전체 기간 연체와 최근 연체를 구분한다.
- 현재 연체정보와 월별 과거 연체정보를 같은 개념으로 합치지 않는다.
- `TARGET`과의 관계는 원인이나 승인정책 효과가 아니라 관측 상관관계로 표현한다.
